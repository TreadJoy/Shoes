## Release flow

`.github/workflows/research-release.yml` has two safe entry paths:

1. A successful `Application CI` run on `main` starts a validation build from
   that run's exact `head_sha`.
2. An owner manually dispatches the workflow with a full commit SHA and target.
   The workflow checks GitHub's `Application CI` check runs for both the
   commerce and research PostgreSQL jobs before it can build or promote.

The build job checks out the exact SHA, installs `requirements.txt` with
`--require-hashes`, runs `pip check`, migrates a clean PostgreSQL database,
checks migration drift, runs Django checks, runs
`check_research_boundary`, `check_research_engagement`, and
`check_release_content`, validates a public-like staging settings profile, and
collects manifest static files. It fails before producing an artifact when any
gate fails. It also rejects every `STRIPE_*` environment variable in the
research build process. The workflow selects `content_profile: private-poc`
only for a manually dispatched `staging` target; all CI-triggered, validation,
and production builds use the fail-closed `public` profile.

The private profile requires staging, research mode, `TREADJOY_PRIVATE_POC=true`,
the noindex response contract, an empty active catalog, and no static or
product media. It permits only the known development-media and labeled
policy-placeholder surfaces. The public profile remains the default and
rejects every non-approved content surface. The former pending-social surface
was removed on 2026-10-13 after the owner approved the four configured URLs.

Each successful build uploads `treadjoy-research-<full-sha>` with a source
manifest, commit timestamp, requirements hash, content profile, check list,
archive, and archive checksum. The artifact is retained for 35 days. Staging
promotion requires a `private-poc` artifact; production promotion requires a
`public` artifact. The current POC's
known development-content blockers intentionally keep the release workflow
from producing a public promotable artifact until content is approved, while
the private staging profile can validate the owner-authorized POC exception.

## Promotion and approval

Manual `staging` promotion downloads and verifies the exact artifact, then
calls the Render API with the exact `commitId`. The adapter waits for a `live`
status and fails if Render reports a different commit. It records the new
deploy ID and the previous live deploy ID in sanitized manifests; those
manifests are retained for 35 days with the release artifact.

Manual `production` promotion must first pass the staging job. It then pauses
at the `research-production` GitHub Environment. Configure the project owner
as the required reviewer for both `research-staging` and
`research-production`. Environment secrets must be created separately for each
environment:

- `RENDER_API_KEY`: a restricted Render API key; never put it in repository
  files or ordinary workflow output.
- `RENDER_SERVICE_ID`: the environment's research web-service ID.

Before using the workflow, configure Render services with automatic deploys
disabled, the reviewed Python 3.12 build/start commands, and the research
secret/database contract. The workflow does not create services, change DNS,
configure Cloudflare, or set secrets.

The adapter follows Render's documented [specific-commit deployment
flow](https://render.com/docs/deploys), [Trigger Deploy API](https://api-docs.render.com/reference/create-deploy),
and [rollback API](https://api-docs.render.com/reference/rollback-deploy).

## Rollback

`rollback-staging` and `rollback-production` require a manual dispatch, the
corresponding protected environment approval, and an explicit prior Render
deploy ID from the retained promotion/rollback manifest. The adapter calls
Render's rollback endpoint and stores a sanitized result artifact. Code
rollback does not imply database rollback; an incompatible migration still
requires the database recovery procedure and owner review.
