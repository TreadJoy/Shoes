## Origin commands

- [`scripts/render_build.sh`](../scripts/render_build.sh) installs the
  hash-locked runtime, runs `pip check`, and collects manifest static files.
- [`scripts/render_start.sh`](../scripts/render_start.sh) checks migration
  drift and deployment settings, then starts Gunicorn on the provider's
  `PORT`. It deliberately does not start against an un-migrated or drifted
  database.
- [`scripts/render_migrate.sh`](../scripts/render_migrate.sh) runs the initial
  and expand migration gate with the separate migrator database URL.
- `requirements.in` and both lock files now include Gunicorn 26.2.0. No
  development server is used by the origin.

The selected free web tier does not provide Render's paid pre-deploy hook, so
the owner runs `render_migrate.sh` once from a controlled Render shell before
the web service is started. The web process then performs only read-only
`migrate --check` validation. A paid or multi-instance deployment must move
this step to a separately controlled pre-deploy/migration service before
scaling.

## Database role sequence

Render's initial Postgres owner is not the application runtime identity. After
the database exists, run [`scripts/provision_research_roles.sh`](../scripts/provision_research_roles.sh)
from a controlled shell with the admin connection and three one-time passwords
provided through environment variables only:

```text
DATABASE_ADMIN_URL=<admin-only Render connection string>
RESEARCH_RUNTIME_DB_PASSWORD=<generated runtime password>
RESEARCH_MIGRATOR_DB_PASSWORD=<generated migration password>
RESEARCH_BACKUP_DB_PASSWORD=<generated backup password>
```

The script creates:

- `treadjoy_research_runtime`: DML only, no database/schema ownership;
- `treadjoy_research_migrator`: schema/migration privileges, no superuser or
  role/database creation privileges; and
- `treadjoy_research_backup`: read-only table access for logical exports.

It also sets default privileges for tables and sequences created by the
migrator by reconnecting as that role (PostgreSQL does not allow the owner
connection to alter another role's default privileges). The script parses the
admin URL into standard libpq environment variables so passwords and
connection strings are not passed as process arguments. Never put any
password or connection string in a repository file or ordinary web-process
environment.

After the role script succeeds, set the web service and any job service's
`DATABASE_URL` to the runtime-role connection string. The Blueprint keeps that
variable `sync: false` intentionally; referencing Render's owner connection
string would violate least privilege.

## TLS, backups, and recovery

The application sets `DB_SSLMODE=require` for the provider URL. The role and
backup scripts set `PGSSLMODE=require` as well. Before any public launch,
verify the provider certificate path and upgrade to `verify-full` with an
approved `DB_SSLROOTCERT` if the selected Render connection supports it.

Free Postgres has no provider PITR or backups, so no recovery guarantee is
claimed for this POC. For portability only, an owner-controlled machine or
approved private job may run
[`scripts/backup_research_postgres.sh`](../scripts/backup_research_postgres.sh)
to create a mode-0600 encrypted custom-format export outside the repository;
this does not establish the one-hour RTO or fifteen-minute RPO. Upgrade to a
paid database and verify its PITR window before accepting durable research
data. The key file, export directory, and database URL must remain outside
source control.

An isolated restore drill, measured RTO/RPO, backup integrity check, and
provider/PITR evidence are still required in Plan 8.

## Email and scheduled jobs

The Blueprint leaves SMTP host credentials and Resend credentials as
`sync: false` values. Populate them only in Render's secret store:

- SMTP remains required for Django operational/error paths and points to the
  one owner mailbox.
- Resend send and webhook credentials belong to the research web service.
- The Resend segment and management key are only needed by contact-sync or
  broadcast jobs; both may remain unset for this no-advertising POC. If a job
  is enabled, the management key belongs only to that job, never the ordinary
  web service.

[`scripts/run_research_jobs.sh`](../scripts/run_research_jobs.sh) is the exact
bounded command for a provider cron job or controlled provider shell. It runs
session cleanup, confirmation delivery, optional contact sync, and report-only
retention. It never enables broadcasts and never applies a draft retention
policy. A Render cron service has a separate minimum charge, so it is
intentionally not included in `render.yaml` until the owner approves that
charge. With the database public allowlist empty, a local scheduler cannot
reach PostgreSQL safely; the private POC therefore uses supervised Render-shell
runs unless a managed cron service or approved private connection is added.

## Staging migration evidence

The clean staging sequence is:

1. Apply `render.yaml` only for the owner-approved Free Postgres POC. Keep its
   database empty except for synthetic/owner test data and record the 30-day
   expiry. Any paid upgrade requires a new price review and approval.
2. Populate the required non-secret host/origin values and secret-store
   entries; keep `ALLOWED_HOSTS` and `CSRF_TRUSTED_ORIGINS` limited to the
   exact research hostname and provider hostname needed for the private test.
   Generate `TREADJOY_ORIGIN_SHARED_SECRET` and provide the same value to the
   Cloudflare overwrite-header rule; never pass it through a client request.
3. Run the role script, replace the owner connection string with the runtime
   role URL, and create only the project owner as the initial admin account.
4. Confirm Render's database is blank, run `render_migrate.sh` with the
   migrator URL, set the web service's `DATABASE_URL` to the runtime-role URL,
   deploy the exact green release SHA, and capture `migrate`,
   `migrate --check`, research boundary, readiness, and redacted log evidence.
5. Keep the hostname behind the approved development-team access perimeter;
   Plan 6 owns Cloudflare DNS, TLS, R2, and origin-bypass verification.

The Free database is the only live resource created by this slice. No web
service, secret, database role, email provider, scheduler, R2 bucket, DNS
record, or staging deployment was created. Plan 6 owns the corresponding
Cloudflare policy and live edge verification.
