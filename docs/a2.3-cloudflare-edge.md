  through `RENDER_RESEARCH_ORIGIN_HOST`.

- Access: default deny with only `ethan@tread-joy.com` allowed. The policy

- Data and credentials: research-only namespace and secret store. Never place

The policy is declarative evidence, not an API call. Run the local validator
before any operator action:

```sh

```

## Safe apply order

1. Export the current Cloudflare DNS records and preserve all existing mail,
   ownership-verification, and other non-web records. Review the export for
   secrets before storing it outside the repository.
2. Confirm the exact Render service hostname and current Cloudflare plan
   capabilities. Create the proxied `research` CNAME only after the origin
   service is ready. Do not add an unproxied direct-origin record.
3. In R2, create the separate research bucket, leave the Public Development
   URL disabled, connect `media.research.tread-joy.com` as its custom domain,
   and verify that no object exists. R2 custom-domain connection creates the
   provider-managed DNS target; do not guess or hard-code that target.
4. Install a valid origin certificate for the Render path, then set the zone
   encryption mode to **Full (strict)**. Set the first HSTS stage to 3,600
   seconds with `includeSubDomains` and preload disabled. Do not claim TLS
   completion until the certificate name, expiry, and Cloudflare handshake are
   verified.
5. Create Cloudflare Access self-hosted applications for both POC hostnames,
   with default deny and an allow policy for exactly `ethan@tread-joy.com`.
   Keep the application protected while testing; public access is a later
   launch decision. Copy the research application's exact audience tag and
   the account's HTTPS team-domain issuer into the Render service as
   `CLOUDFLARE_ACCESS_AUD` and `CLOUDFLARE_ACCESS_TEAM_DOMAIN`; Django verifies
   the signed RS256 application token on every non-health request.
6. Generate a high-entropy `TREADJOY_ORIGIN_SHARED_SECRET` in the Render
   secret store and the Cloudflare rule configuration. Add a request-header
   Transform Rule that **overwrites** `X-TreadJoy-Origin` for requests to
   `research.tread-joy.com`; it must not append a client-supplied value. The
   Django origin rejects requests without the secret and permits only the two
   generic health paths for Render's direct health checker.
7. Deploy the Cloudflare Managed Ruleset to the application and media
   hostnames. Keep Django authorization as the application-level admin gate.
8. Add the two A2.2 rate rules in **log** mode, not enforcement mode. The exact
   application authorities remain 5 waitlist POSTs per session-hour and 60
   survey-step POSTs per session-hour. The exact edge rules are managed
   challenge above 10 waitlist POSTs per IP per 10 minutes for the two approved
   waitlist paths, and above 60 survey POSTs per IP per 10 minutes for
   `/survey/question/*/` only. Review synthetic and ordinary development
   traffic in Security Events, then change the action from `log` to
   `managed_challenge` only after the owner records that review. Do not
   silently merge the rules if the current zone plan cannot support two rules
   and log mode.
9. Add cache rules in this order: bypass unsafe methods and all dynamic/admin,
   account, cart, order, waitlist, survey, webhook, and health paths; cache only
   `GET`/`HEAD` `/static/` on the application host and `/media/` on the R2 host.
   Use one-year edge TTLs for those public, versioned/read-only paths and
   respect the origin browser cache policy. Never cache session-bearing HTML.
10. Add or verify the response headers in the policy, purge affected cache
    entries after header changes, and run the synthetic probe script below.

Cloudflare's current documentation confirms that Full (strict) requires a
valid, matching origin certificate and that Authenticated Origin Pulls can add
an origin-authentication layer; R2 custom domains are the path for caching and
access controls, while `r2.dev` is intended for development and must be
disabled here. See [Full (strict) TLS](https://developers.cloudflare.com/ssl/origin-configuration/ssl-modes/full-strict/),
[Authenticated Origin Pulls](https://developers.cloudflare.com/ssl/origin-configuration/authenticated-origin-pull/),
[R2 public buckets/custom domains](https://developers.cloudflare.com/r2/buckets/public-buckets/),
and [rate limiting rules](https://developers.cloudflare.com/waf/rate-limiting-rules/).

## Live verification gate

After the owner has applied the configuration, run
[`scripts/check_cloudflare_research.sh`](../scripts/check_cloudflare_research.sh)
with the exact `research.tread-joy.com` and
`media.research.tread-joy.com` HTTPS URLs and an owner-only cookie jar. It
checks HTTPS, the edge headers, cache behavior, the generic health response,
owner-only access, and the blank-media 404. Set `REQUIRE_ORIGIN_CHECK=true`
when an `ORIGIN_URL` is supplied so a live verification cannot accidentally
omit the direct-origin test. Then record separately:

- the DNS export comparison and proxied status;
- Full (strict) certificate/handshake evidence;
- Access policy decision for the owner and a denied synthetic identity;
- Django rejection of a missing, expired, wrong-audience, and invalid-signature
  Access JWT, plus acceptance of the owner token issued for this application;
- direct Render-origin requests without and with an invalid origin header;
- rate-limit log events for ordinary traffic and the enforced 429/blocked state;
- managed-WAF event and response evidence;
- R2 object listing showing zero POC objects and `r2.dev` disabled; and
- cache `HIT`/`MISS`/`BYPASS` behavior for static, media, dynamic, and POST
  requests.

These records belong in the external deployment evidence bundle, not in Git.
Until they exist, Plan 6 remains repository-complete but operationally open.
