## Repository rehearsal

Run the safe local rehearsal from the repository root. It writes command logs,
`release-manifest.json`, `owner-acceptance.json`, and `launch-decision.json` to
an evidence directory outside the repository. It does not call Render,
Cloudflare, or any production endpoint.

```sh
./scripts/rehearse_research_release.py \
  --evidence-dir /private/tmp/treadjoy-a2.3-rehearsal
```

The script removes inherited `STRIPE_*` variables for its research process,
uses the explicit research deployment mode, and fails if the evidence
directory is inside the repository. Its expected private-POC result is:

- policy validator, Django checks, focused research smoke/failure tests, and
  Render promotion/rollback adapter tests pass;
- `check_release_content` reports the intentional
  `homepage-development-media` and `pending-social-links` blockers; and
- the generated manifest records `promotable: false` and `launch_decision:
  STOP`.

## Synthetic smoke and failure coverage

`web/core/tests/test_research_rehearsal.py` covers the private research
surfaces with synthetic data:

- homepage, catalog, product detail, waitlist, survey, privacy, terms,
  accessibility, and contact return successfully;
- a missing route returns a generic 404;
- waitlist submission creates only the expected pending synthetic record;
- all survey steps complete once and persist one anonymous response; and
- the sixth waitlist POST reaches the accessible `429` throttle state.

The focused health, observability, and waitlist tests inject database,
provider-email, redaction, correlation, and structured-alert failures. They
verify generic responses, retryable state, and alert records without logging
synthetic secrets or personal data. Elevated-5xx, storage, and scheduler
alerts remain provider-integrated drills, not local claims.

## Immutable artifact and rollback rehearsal

The release workflow in
`.github/workflows/research-release.yml` remains the only promotion path. It
checks out the exact green commit, validates hash-locked dependencies and
research boundaries, creates a checksum-protected artifact, and requires the
protected Render environment for promotion. `scripts/render_release.py` stores
the previous live deploy ID in a sanitized rollback manifest. The adapter
tests in `scripts/tests/test_render_release.py` exercise promotion identity,
previous-deploy capture, rollback recording, and missing-key fail-closed
behavior with a fake API response.

No provider rollback was executed because no Render service or Cloudflare
configuration exists. Application rollback must not be used to undo an
incompatible migration; use the isolated database recovery procedure and
owner review first. Cloudflare rollback requires restoring the reviewed prior
configuration, not guessing records or disabling the origin lock.

## PostgreSQL restore and RTO/RPO gate

The local SQLite database is not restore evidence. After Render PostgreSQL is
provisioned, the owner must:

1. create an isolated restore target from a verified PITR/export point;
2. record source point, restore start/end UTC timestamps, schema/migration
   checks, and synthetic smoke results;
3. measure recovery point against the fifteen-minute RPO target and elapsed
   recovery against the one-hour RTO target; and
4. retain the sanitized provider evidence outside Git with the release
   manifest.

Do not copy customer-like data into the rehearsal. A failed restore or missed
target is a launch stop and follows the database outage runbook.

## External launch gates

The following are intentionally pending for this POC:

- clean Render staging deploy and health/smoke evidence;
- Cloudflare Access, TLS, WAF, cache, media, and direct-origin-bypass evidence;
- PostgreSQL backup/PITR, isolated restore, and measured RTO/RPO evidence;
- injected staging database, storage, email, scheduler, and elevated-5xx
  failures with delivered alerts and runbook tabletop records;
- rollback to the prior Render artifact and prior Cloudflare configuration;
- approved public content, verified social URLs, effective policy pages, and
  automated WCAG/performance evidence; and
- owner acceptance of the release manifest and launch decision.

Until every named gate is recorded and the owner changes the decision, keep
the hostname behind the development-team-only perimeter and do not promote or
advertise the research deployment.
